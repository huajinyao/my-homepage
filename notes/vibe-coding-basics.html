Vibe Coding 入门：把 AI 当搭子，而不是许愿池

滑锦尧 · 2026-09 · 学习笔记 01

这门课第一次让我用「说人话」的方式写代码。一学期下来，我最大的体会是：Vibe Coding 不是一个提示词技巧，而是一套把模糊想法拆成可验证小步的方法。这篇笔记记录我踩过的坑和最后跑通的流程。

它到底是什么

你描述想要什么，AI 生成或修改代码，你负责判断对不对、要不要收。核心分工没变：AI 负责打字，你负责决策。所以「会不会用」的分水岭不在提示词写得多漂亮，而在你能不能一眼看出它哪里改坏了。

我的四步流程

  1. 先定结构，再要样式。第一轮只要「有哪些区块、什么顺序」，不要一上来就要配色和动效。结构错了，后面所有美化都是白做。
  2. 一轮只改一个目标。「加滚动动画」和「改配色」分开提。混在一起，出问题时你不知道是哪一半的锅。
  3. 每次看到效果再继续。改完立刻在浏览器里点一遍，尤其要看手机尺寸——AI 很少主动考虑窄屏。
  4. 小步提交。每轮能跑通就 Git 存一次。AI 有时会「顺手」改坏别的地方，有提交点才能干净地退回去。

提示词里必须有的三样东西

我总结出一个能显著提高命中率的模板，缺一样效果就明显变差：

  • 约束：技术边界。「只用原生 JS，不引入新依赖」「配色 #0a0e14 + #00e5ff」。
  • 上下文：现状。「现在导航栏是 fixed，移动端用汉堡菜单」。
  • 验收标准：怎么算成功。「手机上粒子数降到 40，滚动不卡」。
反例：「帮我做得好看一点」。这句话信息量为零，AI 只能猜，猜错你还得重来。

一个真实案例：粒子网络要不要砍

V2 加了 Canvas 粒子网络，电脑上很好看，手机上直接卡死。AI 的第一版建议是「换成静态 SVG 或纯 CSS 渐变」——从性能角度没错，但那等于把这一版的视觉核心砍掉了。

我拒绝了这个方案，改成按屏幕宽度降级：小于 1024px 用 70 个粒子，小于 768px 用 40 个、30fps，小于 480px 用 20 个。效果保住了，手机也不卡了。

这件事让我记住一条：AI 会给你「最安全」的方案，但最安全往往等于最平庸。你得知道自己要什么，才敢否决它。

三个反复踩的坑

  • 它悄悄改了别的地方。要它改导航，它顺手动了卡片样式。对策：每轮只让它输出改动的那一段，别整文件重写。
  • 它「看起来对」但跑不起来。变量名对不上、类名拼错。对策：改完立刻在控制台看报错，不要攒着。
  • 它不知道你的真实约束。它不知道你的手机多卡、你愿不愿意维护数据库。这些必须你自己判断。

收工前的自查清单

  1. 桌面和手机各点一遍，有没有溢出、错位
  2. 控制台有没有红色报错
  3. 所有链接点一遍，有没有 404
  4. 内容是不是真实的（不虚构经历、不编数据）
  5. Git 有没有存下这个能跑的版本

最后一句：Vibe Coding 让我做得更快，但没有让我变懒——判断力仍然是自己的。AI 给的是选项，选哪个、为什么选，还得自己说得出理由。
